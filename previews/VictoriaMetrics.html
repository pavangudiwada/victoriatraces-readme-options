Why VictoriaMetrics?

  • Keep your Prometheus workflow. Use Prometheus remote write, PromQL-compatible queries, and your existing Grafana dashboards. Prometheus integration.
  • Start with fewer moving parts. The single-node database runs as one binary without an external database. Move to independently scalable ingestion, query, and storage components when you need a cluster. Deployment options.
  • Query across your metric sources. Collect from multiple Prometheus servers or supported ingestion protocols and query the data together with MetricsQL.
  • Evaluate with evidence. Read how Grammarly, Roblox, Wix, and other teams run VictoriaMetrics, then test with your own workload.

Try it locally

With Docker installed, start a single-node instance that collects its own metrics:

docker run --rm --name victoriametrics \
  -p 127.0.0.1:8428:8428 \
  -v victoriametrics-data:/victoria-metrics-data \
  victoriametrics/victoria-metrics:v1.155.0 \
  -storageDataPath=/victoria-metrics-data -selfScrapeInterval=5s

After about 30 seconds, open VMUI and run:

process_resident_memory_bytes

You should see the database process's resident memory usage. The named Docker volume preserves data between runs. For binaries, Kubernetes, and collecting application metrics, follow the full quick start.

How it works

The diagram shows a typical collection path. Single-node VictoriaMetrics can also scrape targets directly. In a cluster, vminsert accepts writes, vmstorage stores data, and vmselect serves queries. Architecture and sizing.
